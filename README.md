# WHY — minitrace をなぜ作るか

> 迷ったら、この文書を読むだけにする。方針の再検討はしない。

## 前提（なぜやるか）

低レイヤセキュリティに進むには、プログラムが動くときに OS との間で何が起きているかを、
読んだ知識だけでなく、自分の手で確かめた経験が必要であると思った。
C は目的ではなく、道具として使う。
OS を学んでから作るのではなく、作りながら必要になった分だけ掘るという学習の方向性。

## なぜ OS の挙動が低レイヤセキュリティにつながるのか（根拠）
 
思い込みではなく、既存の防御技術がどこで動いているかで裏を取る。
 
### 根拠1 — 防御の判定が「システムコールの番号と引数」で行われている
 
Linux の seccomp-BPF は、プロセスに許可するシステムコールを制限する仕組み。
判定用のプログラムがシステムコールの番号と引数を読み、実行される前に
許可・拒否を決める。
 
実例：32 ビット版 open() は番号 5、64 ビット版 openat() は番号 257。
番号だけ見て動作環境を確認しないフィルタは、32 ビット側の呼び出し方で回避される。
 
→ minitrace の W3（番号を名前に直す）・W4（引数を読む）は、
  防御側が判定に使っているのと同じ対象を扱っている。
 
出典: https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html
 
### 根拠2 — 侵入検知の主要製品が、システムコールの流れを見て判定している
 
Falco はカーネルに組み込まれて動作を監視する検知ツールで、
システムコールを既定のデータ源とする。Tetragon、Tracee も同じ発想。
Tetragon は検知に加え、システムコールを実時間で遮断もする。
 
→ minitrace は「システムコールの流れを取って集計する」部分を
  規模を落として自作するもの。構造が同じ。
 
出典: https://falco.org/about/faq/
 
### 根拠3 — C のメモリ管理は、脆弱性の最大の発生源そのもの
 
Microsoft の CVE の約 70%、Chromium の脆弱性の約 70% がメモリ安全性の問題。
Mozilla では重大・高深刻度 34 件中 32 件。Project Zero の集計では
2021 年のゼロデイの 67%。
 
出典: https://www.cisa.gov/resources-tools/resources/case-memory-safe-roadmaps
 
### 根拠3 への反証（ここを曖昧にしない）
 
同じ資料は、C/C++ から Rust 等への移行を勧告している。
新規開発で C を選ぶことは推奨されていない。
したがって「C を書けること」自体の価値は今後下がる。
 
正しい立て方はこうなる：
既存の攻撃対象が C で書かれており、その挙動を観測・分析する側に回るために、
読めて追える必要がある。C を書くのは、観測する道具を自分で作るため。

## 完成時に説明できること 5 つ

### 1. プログラムが別のプログラムを起動するとき、OS の中で何が起きているか

実行中のプロセスが自分の複製を作り、その複製を別のプログラムに置き換え、
終わるまで待つ。この一連の流れを、自分が書いたコードを指しながら説明できる。
「プログラムを実行する」という操作が、
実際には複数の段階に分かれていることを、動く実物で示せるようになる。

### 2. あるプロセスの動作を、別のプロセスから観測する仕組み

OS は、あるプロセスが別のプロセスを監視下に置くための仕組みを用意している。
これを使うと、監視される側が OS に何かを依頼するたびに実行を一時停止させ、
その内容を記録してから再開させられる。
監視する側とされる側がどう同期しているのか、
止まっている間に何が読めるのかを、実装した立場から説明できるようになる。

### 3. プログラムと OS の間で、情報がどう受け渡されているか

プロセスが OS に処理を依頼するとき、依頼の種類と引数は決まった場所に置かれる。
その置き場所の規約を調べ、そこから値を読み出して意味のある形に直した。
関数呼び出しの裏側で実際に何が動いているかを、具体的に説明できるようになる。

### 4. 自分で確保したメモリを、自分で管理した経験

必要な量を実行中に確保し、使い終わったら返す。返し忘れがないことを
検査ツールで確認した。どこで確保し、どこで返すかを自分で決める必要があること、
それを怠ると何が起きるかを、実際に書いた立場から説明できるようになる。

### 5. 不具合を、推測ではなく手順で特定した経験

意図的に仕込んだ不具合と、作る過程で自然に出た不具合の両方を、
デバッガと検査ツールで追い、原因を特定する。
「動かない」から「ここが原因」までを、どういう順序で詰めたかを説明できるようになる。
あわせて、本物の strace と出力を比較し、
自作物が何をできて何をできないかを伝えることができるようになる。

## 使い方

- 手が止まったとき、題材を変えたくなったときに読む。
- ここに書いた 5 つが言えるようになっていれば、完成の定義を満たしている。
- 5 つの中身を書き換えるのは、週次計画そのものを見直すときだけにする。
